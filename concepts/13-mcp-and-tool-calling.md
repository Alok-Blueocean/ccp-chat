# MCP (Model Context Protocol) & Tool Calling Concepts

General knowledge — not used in this repo, but a near-certain topic in any 2026-era AI engineering interview.

| Concept | What it is | Key details | Interview angle |
|---|---|---|---|
| **The problem MCP solves** | Before MCP, every agent framework wired up tools/data sources to models with its own bespoke integration code — an N×M problem (N models/frameworks × M tools). | MCP standardizes the interface between an AI application and external tools/data as a client-server protocol, so a tool built once can be used by any MCP-compatible client. | Framing it as "solving the N×M integration problem, like LSP did for editors↔languages" is a strong, precise analogy interviewers recognize. |
| **Client-server architecture** | An **MCP host** (the AI app, e.g. Claude Code) runs one or more **MCP clients**, each connecting to an **MCP server** that exposes tools/data for one system (GitHub, a database, Slack, ...). | Servers are typically separate processes — the model itself never talks to the server directly, the host mediates every call. | Know the three-role vocabulary precisely: host, client, server — interviewers who work with MCP will notice if you conflate "client" and "host." |
| **Primitives: Tools, Resources, Prompts** | **Tools** = callable actions with typed args (like function calling). **Resources** = readable data the host can fetch and inject into context (files, query results). **Prompts** = reusable, parameterized prompt templates a server can expose. | Tools are model-invoked (the LLM decides to call them); Resources are typically host/user-invoked (attached deliberately, not model-chosen) — that distinction is the most commonly missed detail. | Being able to say "tools are model-driven, resources are usually host-driven" shows real hands-on understanding vs. having only read the spec summary. |
| **Transports** | stdio (local subprocess, most common for local dev tools), HTTP+SSE / streamable HTTP (remote servers, e.g. a hosted SaaS integration). | Local stdio servers inherit the host's permissions directly (no network hop); remote servers need their own auth (OAuth, API keys) independent of the host's. | Ties directly into a real operational concern: interactively-authenticated remote MCP servers (OAuth) don't work in headless/non-interactive environments — a genuine gotcha, not trivia. |
| **Tool discovery / schema loading** | An MCP client can query a server for its available tools and their JSON schemas at connection time, rather than the host hardcoding what any given server offers. | This is why MCP tool lists can be large and dynamic — a host might defer loading full schemas until a tool is actually likely to be used (schema-on-demand), rather than stuffing every tool's full schema into every prompt. | Explains a real design pattern: lazy/deferred tool schema loading exists specifically to avoid bloating context with tools that won't be used in a given turn. |
| **MCP vs. plain function/tool calling** | Function calling is the *model-level* mechanism (structured output matching a schema). MCP is a *protocol* for how an application discovers, connects to, and invokes those tools across process/network boundaries in a standard way. | You can have function calling without MCP (a single app wiring its own tools directly), and MCP without changing how function calling itself works under the hood — MCP standardizes the plumbing, not the model capability. | The precise way to answer "isn't MCP just function calling?" — no, function calling is the model primitive MCP's tool-calling sits on top of. |
| **Security surface** | Because tool results (and resource content) flow back into the model's context, a malicious or compromised MCP server can perform indirect prompt injection — the same threat named in [08-guardrails-and-llm-safety-concepts.md](08-guardrails-and-llm-safety-concepts.md). | Trust boundaries matter: a tool's *output* should be treated with the same skepticism as any other untrusted retrieved content, even though the tool call itself was "requested" by the model. | Connects two concepts directly — MCP tool results are exactly the kind of untrusted, model-consumed content that indirect prompt injection defenses need to cover. |
| **Where this fits vs. agents** | MCP is the *integration layer* (how an agent gets access to tools/data); the agentic loop, planning, and memory concepts in [07-ai-agents-concepts.md](07-ai-agents-concepts.md) are the *control-flow layer* that decides when/how to use them. | An agent can use MCP-provided tools exactly like any other tool in its ReAct loop — MCP doesn't change the loop, it changes where the tool definitions come from. | Useful closing line if asked to relate MCP to "agents" broadly — they answer different questions (what tools exist / how they're wired vs. how the model decides to use them). |
